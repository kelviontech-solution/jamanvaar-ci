## Critical

### CRIT-01 — Any device token can forge staff identity via cloud entity-sync (root cause of ~⅓ of this register)
- **Sources:** `api-device-sync.md` DS-01 · `pos.md` POS-01 · `pos-admin.md` POSADMIN-02 · `kds-captain.md` KDSCAP-01/02 · corroborated by `api-data.md` AD-14, `local-core-packages.md`
- **Where:** `cloud/api/src/modules/entity-sync/entity-sync.controller.ts:16-34`, `entity-sync.service.ts:33-98`, `dto/push-entity-sync.dto.ts:15-31`
- **What:** `EntitySyncController` is gated only by `DeviceAuthGuard` — proof that *some* device of this restaurant is active — with **no check on `device.type`** anywhere, for any of the 11 `SYNCABLE_ENTITY_TYPES` including `STAFF_USER`. The payload schema is `z.record(string, unknown)` — completely unstructured. `STAFF_USER` isn't even in the "last-change-wins" conflict set, so a push always lands unconditionally.
- **Attack:** A customer-facing Kiosk or kitchen KDS device token (the lowest-trust credentials in the system, sitting in plaintext `localStorage`) can `POST /api/v1/entity-sync/STAFF_USER` with `{roleId: "role-manager", pinHash: <self-computed>}`. Every POS/POS-Admin/Captain terminal pulls and applies it within 15 seconds (`applyRemoteUser` in `packages/database/src/repositories.ts:3274-3298` accepts `roleId`/`pinHash`/`isActive` verbatim, keyed by id, no signature check). The same gap lets a low-trust device *read* every existing staff member's PIN hash for offline cracking (trivial — see MED-08), tamper with `MENU_ITEM`/`MENU_CATEGORY` prices, `COUPON`, `CUSTOMER` PII, and `INVENTORY_ITEM`.
- **Impact:** Full privilege escalation from a customer-facing terminal to a fleet-wide manager identity — unlocks refund/void/discount/day-close on every POS terminal in the restaurant.
- **Fix:** In `EntitySyncController.push`/`pull`, add a per-entity-type allowlist keyed on `device.type` (e.g. only `POS_ADMIN` may write `STAFF_USER`; strip `pinHash` from any pull by a non-admin device type). Give `STAFF_USER` a real Zod schema instead of `z.record(unknown)`. Longer-term, require role elevation to go through an authenticated tenant-JWT session, mirroring `TenantAuthService.createStaffUser`'s existing `actor.role === 'OWNER'` check.
- **Regression test:** e2e — a `KIOSK`/`KDS`/`CAPTAIN` device token POSTing `STAFF_USER` with `roleId:'role-manager'` must 403; the same from `POS_ADMIN` must succeed; a `GET` from a non-admin device type must never include `pinHash`.

### CRIT-02 — Any tenant user can mark their own SaaS invoice paid and un-suspend the subscription
- **Sources:** `api-license-billing.md` LB-01 (re-verifies old F-001) · independently confirmed in `pos-admin.md`
- **Where:** `cloud/api/src/modules/billing/tenant-billing.controller.ts:11,40-48`, `billing/invoices.service.ts:816-917`
- **What:** `POST /api/v1/tenant/billing/invoices/:id/pay` is gated only by `TenantAuthGuard` — **any** logged-in tenant user, including STAFF, can call it. The handler inserts a `COMPLETED` Payment row, marks the invoice `PAID`, and sets `subscription.status = 'ACTIVE'` — with no call to Razorpay or any payment gateway. It also **un-suspends a platform-suspended subscription** (the update unconditionally forces `status: 'ACTIVE'`) and accepts payment against `VOID`/`REFUNDED` invoices.
- **Attack:** Any STAFF login (even one created for a completely different purpose) at a restaurant with a lapsed or platform-suspended subscription calls this one endpoint with an empty body and gets unlimited free service, forever (renewal invoices auto-generate 7 days before expiry, so the exploit repeats indefinitely with no further action).
- **Impact:** Unlimited SaaS revenue bypass; falsified payment/collection records; a platform-side suspension (used for abuse/non-payment) is silently reversible by the suspended tenant itself.
- **Fix:** Delete this endpoint or make it create a real Razorpay order/session instead of a direct DB write; settle invoices only from the verified webhook handler; restrict any tenant billing mutation route to OWNER; never touch a `SUSPENDED` subscription from a tenant-initiated call; reject non-`ISSUED/PAST_DUE` invoice states.
- **Regression test:** STAFF token → `/pay` returns 403 and invoice/subscription state is unchanged; a `SUSPENDED` subscription stays suspended after any tenant-initiated payment call.

### CRIT-03 — The shipped prebuilt LAN-core binary is built from the unauthenticated (pre-fix) server, not the patched one
- **Source:** `local-core-packages.md` LOCAL-01
- **Where:** `tooling/local-runtime/sea-config.json:2` (declares `main: standalone_local_core.cjs`), `standalone_local_core.cjs:1-178` (whole file: `HOST=0.0.0.0`, `Access-Control-Allow-Origin: *`, zero auth on `/api/orders`/`/api/events`), `tooling/installers/build_release.cjs:23,276,517` and `build_production_release.ps1:121,447,451,478` (both bundle the tracked `JamanvaarLocalCore.exe` binary directly)
- **What:** Two independently-evolved copies of the same LAN order-server exist in the tree. `local_service.cjs` received a real "SEC-005" authentication fix (a per-install service key required on every data-bearing endpoint). `standalone_local_core.cjs` never did. The committed 93MB `JamanvaarLocalCore.exe` was proven — via `sea-config.json`'s own declared entry point, plus literal ASCII strings found inside the binary (`"JAMANVAAR Local Core Engine"` present, `"SEC-005 fix"`/`"Pairing PIN for new devices"` absent) and file timestamps (binary built Sep 1; the fix landed in `local_service.cjs` Sep 6, five days later, with the binary never rebuilt) — to be compiled from the **unfixed** file. Two of the several installer-build scripts in the repo (`build_release.cjs`, `build_production_release.ps1` — the two whose names most suggest the authoritative "release" path) package this stale binary directly; the other installer scripts correctly bundle and `node`-launch the patched `local_service.cjs` source instead.
- **Impact:** If `build_release.cjs`/`build_production_release.ps1` is the packaging path actually used for real customer installers, every restaurant using it runs a LAN order server with **zero authentication**, reachable by anyone on the same WiFi/LAN (guest network, a nearby table, a compromised IoT device on the same subnet) — full read of all orders (including customer name/phone), unrestricted order injection, and a live unauthenticated event stream of restaurant activity.
- **Fix:** Delete `standalone_local_core.cjs`, `sea-config.json`, `sea-prep.blob`, and the tracked `.exe`; repoint the two divergent installer scripts at `local_service.cjs` like every other installer script already does. Stop committing multi-hundred-MB binaries to git — build in CI, sign, publish as a release artifact.
- **Regression test:** CI check that fails the build if any installer script references a source file lacking the `isAuthorized`/service-key pattern; a smoke test that launches whatever `build_release.cjs` actually packages and asserts `GET /api/orders` returns 401 without a key.

## High

### HIGH-01 — Support search/diagnostics leak full credential rows, including an unsalted password-reset OTP hash, to READ_ONLY staff
- **Sources:** `api-data.md` AD-01 · `super-admin-web.md` SAW-01 · independently re-confirmed in `api-auth.md`
- **Where:** `cloud/api/src/modules/support/support.service.ts:24-86` (`search`), `:88-147` (`getDiagnostics`); route gate `common/rbac/access.ts` grants `support:'read'` to READ_ONLY, SUPPORT_ADMIN, PLATFORM_OPS
- **What:** Both methods `include` related rows with **no `select`**, returning full `User`/`Device`/`ActivationKey` Prisma models — `passwordHash` (bcrypt, harvestable for offline cracking), `activationTokenHash`, `deviceTokenHash`, and — critically — **`passwordResetHash`**, which is an **unsalted SHA-256 of a 6-digit reset OTP** (`hashOpaqueToken(otp)` in `tenant-auth.service.ts:820`; `hashOpaqueToken` = plain `sha256`, `token.util.ts:9-11`).
- **Attack:** (1) Trigger the public `POST /tenant-auth/forgot-password` for a known owner email (stores the OTP hash, valid 15 min). (2) As READ_ONLY: `GET /support/search?q=<owner email>` → `passwordResetHash`. (3) Offline, hash all 10⁶ six-digit strings with SHA-256 (well under a second) to recover the OTP. (4) `POST /tenant-auth/reset-password` with the recovered OTP inside the 15-minute window — the 5-attempt online limit never applies because only one *online* call is needed.
- **Impact:** The lowest-privileged platform role can take over any tenant owner's account. This also bypasses the entirely separate, audited, role-gated "impersonate" feature the product already has for legitimate support access.
- **Fix:** Replace `include` with explicit `select` allow-lists in `support.service.ts` (mirror the pattern already used correctly in `owners.service.ts`/`restaurants.service.ts`). Separately, key the reset-OTP hash with a server-side HMAC secret rather than a bare SHA-256, so a leaked row alone isn't sufficient even if this or a similar leak recurs elsewhere.
- **Regression test:** e2e as READ_ONLY — call both endpoints for a user with a live reset OTP in flight, assert the response contains none of `passwordHash|activationTokenHash|passwordResetHash|deviceTokenHash` at any depth.

### HIGH-02 — Low-privilege platform roles can read live activation codes and mint device credentials for any tenant
- **Sources:** `api-license-billing.md` LB-04 · `api-data.md` AD-03 · `super-admin-web.md` SAW-02
- **Where:** `activation-keys.service.ts:44-51,86-90` (list returns plaintext `code` for AVAILABLE keys), `:163-172` + controller (`GET :id` bypasses redaction entirely), `restaurants.service.ts:192` (restaurant detail returns raw `activationKeys` including `code`), `support.service.ts:73-80`; all gated only by `devices:'read'`/`restaurants:'read'`, held by READ_ONLY and SUPPORT_ADMIN; the redeem endpoint itself is public by design (`activation-keys.service.ts:243-262`).
- **Attack:** `GET /activation-keys?lifecycle=AVAILABLE` (or `/restaurants/:id`, or `/support/search`) returns a redeemable code → `POST /activation/redeem {code, deviceType}` (unauthenticated) → a long-lived, non-expiring device bearer token for that tenant.
- **Impact:** A read-only platform role can enroll a rogue terminal into any restaurant and, from there, reach every device-token-authorized surface — order sync, entity sync (see CRIT-01), refunds (if the key allows a POS-family device type), receipts relay.
- **Fix:** Return the plaintext code only once, in the generation response; store a hash thereafter and show only `codeLast4`; require `devices:'write'` to view the full code anywhere it currently leaks; strip `code` from audit-log details.
- **Regression test:** As READ_ONLY, list/detail/audit/search responses must contain no full redeemable code; a redeem attempt using a value taken from those responses must fail.

### HIGH-03 — Read-only platform roles can download full decrypted tenant backups, unaudited
- **Sources:** `api-license-billing.md` LB-05 · `super-admin-web.md` SAW-10 (re-verifies old F-035)
- **Where:** `common/rbac/access.ts` (backups route maps to `ops`; READ_ONLY/SUPPORT_ADMIN hold `ops:'read'`), `backups/platform-backups.controller.ts:22-37`, `backups.service.ts:199-222` (server-side decrypt-and-stream, or a presigned URL for unencrypted objects) — no audit-log call on either download path.
- **Attack:** `GET /restaurants/:id/backups` → `GET .../:bid/file` with a READ_ONLY session returns the full decrypted backup — branches, staff emails/phones, every synced customer, every synced order, staff PIN hashes.
- **Impact:** Bulk PII/financial exfiltration by a role meant to be strictly read-only, and it leaves no audit trail.
- **Fix:** Add a dedicated, stricter area rule for the download/file routes (owner-level only, or a new write-level "backups:download" permission); log every download.
- **Regression test:** READ_ONLY/SUPPORT_ADMIN get 403 on `/download` and `/file`; an allowed download by an owner-level role produces an audit row.

### HIGH-04 — POS-Admin login never restricts to OWNER/MANAGER; any tenant role gets the full admin console
- **Source:** `pos-admin.md` POSADMIN-01
- **Where:** `pos-admin/src/cloud/cloudClient.ts:254-281` (login body sets `deviceType:'POS_ADMIN'` but never `adminOnly:true`, unlike `kiosk-admin`'s equivalent call which does send it), `cloud/api/.../tenant-auth.service.ts:281` (`adminOnly` is honored only if the *client* sends it), `App.tsx:226-232` (any non-OWNER role is mapped straight to `role-manager` locally, with zero further permission checks anywhere in the app).
- **Attack:** A STAFF-role login (e.g. a Captain credential the owner minted for floor use) used against an activated POS-Admin terminal returns `LOGIN_SUCCESS` and is immediately treated as a manager: full staff/PIN administration, price/menu edits, PII export, refund initiation, cloud-backup upload/download, invoice "pay".
- **Impact:** Privilege escalation from any floor-level login to the full restaurant admin console on any POS-Admin terminal.
- **Fix:** Server-side, reject `deviceType==='POS_ADMIN'`/`'KIOSK_ADMIN'` logins for any role below MANAGER regardless of what the client sends (don't trust the client-supplied `adminOnly` flag at all). Client-side, refuse to complete an admin session for a STAFF-role login as defense-in-depth.
- **Regression test:** Cloud e2e — STAFF login with `deviceType:'POS_ADMIN'` returns 403.

### HIGH-05 — Order-sync: no branch isolation on read, no ownership/state-machine check on write
- **Sources:** `api-device-sync.md` DS-02/DS-03 · `pos.md` POS-05 · `kds-captain.md` KDSCAP-04 (re-verifies old F-014/F-043)
- **Where:** `cloud/api/src/modules/order-sync/order-sync.service.ts:56-93` (push: plain upsert by `(restaurantId, externalOrderId)`, no device-type/ownership/state-machine check), `:127-139` (`catchUp`: filtered only by `updatedAt`, **no `branchId` filter** despite `Device.branchId`/`SyncedOrder.branchId` both existing in the schema).
- **Attack (read side):** Any device token bound to one branch of a multi-branch restaurant pulls **every branch's** orders, including `meta.customerName`/`meta.customerPhone`. **Attack (write side):** any device token — including a stale/offline Captain or KDS tablet reconnecting — can push a conflicting `paymentStatus`/`totalAmount` for an already-settled order, and the server accepts it unconditionally (design comment in the code openly says totals are "trusted as-is... not a payment-authoritative record", but POS treats the mirror as authoritative when it pulls it back).
- **Impact:** Cross-branch PII/financial disclosure; a compromised or merely stale low-trust device can revert a paid order's status or alter its recorded total, corrupting cash reconciliation and sales reporting.
- **Fix:** Add `branchId: device.branchId` to the `catchUp` query. Reject a push that changes `paymentStatus` away from a terminal state unless the pushing device is the order's original device or is POS/POS_ADMIN type; use a `syncVersion`/compare-and-set instead of last-write-wins for money fields.
- **Regression test:** A branch-A device token's pull must return zero branch-B rows; a stale/conflicting push to a `PAID` order's `paymentStatus` must be rejected or flagged as a conflict, not silently applied.

### HIGH-06 — A working SUPER_ADMIN credential is committed to git in plaintext

## Findings explicitly considered and rejected or downgraded

To keep this register honest, these are old-audit claims or candidate issues that **did not** survive re-verification at CRITICAL/HIGH severity, with the reason:

- **"JWT verification doesn't pin algorithm, shares secret across realms" (old F-023):** the shared HMAC secret is real, but every `verifyAsync` call pins `issuer`/`audience` per realm, which `jsonwebtoken` enforces — a token forged for one realm is rejected by the other guard even with the same secret. No live cross-realm bypass exists. Downgraded to a hardening note (pin `algorithms: ['HS256']` explicitly as defense-in-depth).
- **"LAN command pipeline trusts a self-declared sender role" (old F-032):** the code exists but is dead — referenced only by one test file, and the "LAN mesh" transport is same-browser-origin `BroadcastChannel`/`localStorage`, never a real network hop. Not exploitable by a remote/LAN attacker as shipped.
- **"Kiosk connects to an untrusted host from a UDP beacon" (old F-029):** the vulnerable Rust command (`discover_local_core`) is real and unauthenticated, but grepping the entire Kiosk frontend found **zero callers** of it — it is unreachable from the shipped app today. Recorded as a real-but-dormant issue (kiosk.md KIOSK-01), not a live one.
- **".local_service_key committed in git" (old F-033's secret claim):** false at HEAD — the file is correctly gitignored and was not found tracked.
- **CSV header-injection via report `type` param (part of old F-038):** false — Node's `setHeader` rejects CR/LF, so response-splitting via that vector isn't possible; only the (confirmed) formula-injection half of F-038 survives.

See [`OLD-AUDIT-VERIFICATION.md`](OLD-AUDIT-VERIFICATION.md) for the disposition of all 47 original claims, not just these five.
