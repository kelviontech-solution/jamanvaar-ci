## New/independent findings

### KIOSK-01 `send_escpos_bytes` allows arbitrary outbound TCP from the kiosk webview with no destination allowlist
- Severity: medium (same class/reasoning as `pos.md`'s downgrade of the equivalent POS finding — no HTML-injection sink was found in the ~1275 lines of `kiosk-user/App.tsx` read, or anywhere via the repo-wide XSS-sink grep across both kiosk apps, so exploitation needs an external script-injection primitive this audit did not find); Class: CONFIRMED
- CWE-918 (SSRF-equivalent via native IPC) / CWE-284
- `apps/kiosk-system/kiosk-user/src-tauri/src/main.rs:98-115`, `apps/kiosk-system/kiosk-admin/src-tauri/src/main.rs:5-22` (identical command in both apps)
- Attacker/precondition: any JavaScript able to call a Tauri `invoke()` in the kiosk webview — either a future first-party bug, or a compromised dependency, since `tauri.conf.json`'s `"security": {"csp": null}` (confirmed in both `kiosk-user`/`kiosk-admin` configs) places no restriction on script sources, and neither `src-tauri` directory has a `capabilities/` file scoping which commands the window may call (confirmed via `find -iname "*capabilit*"` — none in either app).
- Repro: `invoke('send_escpos_bytes', { ip: '10.0.0.5', port: 3389, bytes: [...] })` opens a raw TCP connection from the kiosk machine to any host:port reachable on its network, with no allowlist of expected printer subnets/ports (contrast with `packages/native/printing.rs`'s `scan_network_printers`, which *does* restrict scanning to private subnets — this separate raw command bypasses that entirely).
- Impact: if a script-injection primitive is ever found in either kiosk app, this command turns it into a pivot point to internal network hosts/services reachable from the kiosk's LAN position (which, per the product's own architecture, is the same restaurant LAN as POS, KDS, and the Local Core service) — port-scanning, banner-grabbing, or sending arbitrary bytes to internal management interfaces.
- Root cause: the raw ESC/POS command trusts its `ip`/`port` arguments completely; there is no allowlist check, unlike the sibling `printing.rs` module's subnet-scoped scanner.
- Fix: either remove `send_escpos_bytes` in favor of the already-safer `print_raw_system`/`print_serial`/`scan_network_printers` path, or add the same private-subnet/allowed-port validation `printing.rs` already implements for network printer scanning before opening the connection. Also add a `capabilities/default.json` scoping the main window to only the commands it actually needs.
- Regression test: a Rust unit test asserting `send_escpos_bytes` rejects a non-private-range IP (e.g. a public IP or `169.254.x.x` link-local) the same way `scan_network_printers` already does.

### KIOSK-02 No Tauri capabilities file in either kiosk app — every registered command is exposed to the main window with no explicit scoping
- Severity: low/hardening (compounds KIOSK-01's impact rather than being independently exploitable); Class: CONFIRMED
- CWE-284 (Improper Access Control)
- `apps/kiosk-system/kiosk-user/src-tauri/` and `apps/kiosk-system/kiosk-admin/src-tauri/` — no `capabilities/*.json` in either (confirmed via `find`); `tauri.conf.json` also has no inline `app.security.capabilities` entry in either app.
- Impact: this is Tauri v2's recommended defense-in-depth layer (explicitly scoping which windows may call which commands) being entirely absent — every one of the 6-9 registered commands (including `send_escpos_bytes`, and for `kiosk-user`, `discover_local_core`/`test_core_connection`/`get_machine_ip`) is callable from any script that ends up running in the main window.
- Fix: add an explicit `capabilities/default.json` for each app listing only the commands the production UI actually calls.
- Regression test: N/A (config hardening) — could add a build-time check that `tauri.conf.json`/capabilities exist and are non-empty.

### KIOSK-03 No attempt limit on the kiosk's manager-PIN discount override — a walk-up customer can brute-force it offline
- Severity: medium; Class: CONFIRMED
- CWE-307 (Improper Restriction of Excessive Authentication Attempts) / CWE-916 (weak hash, compounding factor — see F-030)
- `apps/kiosk-system/kiosk-user/src/App.tsx:1240-1266` (`handleStaffPinVerify`)
- Attacker/precondition: physical access to any customer-facing kiosk terminal (its entire purpose — no special access needed) with enough patience to enter PINs repeatedly.
- Repro: `handleStaffPinVerify` calls `StaffRepository.verifyPin(staffPin)` — a synchronous, fully local/offline check (per `pin.ts`, a fast FNV-1a hash comparison, no network round-trip) with **no attempt counter, cooldown, or lockout** anywhere in the handler or the surrounding component. A customer can enter all 10,000 four-digit PINs from the on-screen keypad (or drive it programmatically if any injection primitive exists) with no server visibility until one succeeds (the code does correctly restrict the *effect* to `isManager` users only, and does log every attempt to `AuditRepository` — see Controls section — but nothing blocks the attempts from continuing).
- Impact: on success, the customer (a) receives an unauthorized 10% "Manager Discount" on every order at that kiosk from then on (`setStaffOverrideActive(true)`, applied automatically per line 671, with no re-entry required per session), and (b) — more importantly — has now discovered a real manager's working 4-digit PIN, which (per `local-core-packages.md` F-030/pin.ts) is the *same* credential used to log into POS/POS-Admin/Captain/KDS as that manager, and which (per `api-device-sync.md` DS-01) can otherwise only be obtained by a device with cloud entity-sync access. A public kiosk with unlimited offline PIN attempts is the softest target in the whole PIN-based trust model, since it requires no device token, no network position, and no prior access — only being a customer standing at the terminal. The still-shipped default weak PINs (`9999`/`5678`/`1234` in `live_db.json`, confirmed in `local-core-packages.md`) make this immediately exploitable on any restaurant that hasn't changed them.
- Root cause: `verifyPin` has no attempt-throttling wrapper; the manager-override feature was built assuming a well-intentioned staff member, not a hostile customer with a public terminal in front of them.
- Fix: add a per-session (or per-kiosk, persisted) failed-attempt counter with an escalating lockout (e.g. 5 wrong PINs → 60s lock, doubling), and consider requiring a manager PIN to be re-verified against the cloud (or at minimum rate-limited server-side via the heartbeat/audit channel) rather than purely offline, given the outsized blast radius (a working staff PIN) of a successful guess.
- Regression test: simulate 50 wrong-PIN attempts in under a few seconds against `handleStaffPinVerify`/`StaffRepository.verifyPin`; assert the UI locks out well before the full keyspace could be tried, and that a correct PIN is rejected while locked out.

## Controls verified OK
- No `dangerouslySetInnerHTML`, `.innerHTML =`, or `eval(` anywhere in either kiosk app's source (repo-wide grep across `kiosk-user/src` and `kiosk-admin/src`) — no first-party XSS sink found.
- Kiosk payment flow never trusts a client-side "success" belief: `getPaymentOrderStatus` polling only reflects the server's own recorded Cashfree status, and the local order total is reconciled to the cloud's authoritative price before checkout proceeds (`App.tsx:1021-1025`).
- `handleFullSessionReset` (lines 616-663) is thorough — clears cart, customer account, staff override, feedback, chat, E-Bill state, and cancels any in-flight speech synthesis, on both idle timeout and post-confirmation, which is the right control for "no customer data leaks between guests" (the code's own comment references this intent).
- `handleStaffPinVerify` does correctly gate the discount behind `verified?.isManager` (not just any valid PIN) and logs both success and failure to `AuditRepository` — the finding above (KIOSK-03) is about missing rate-limiting, not a missing role check (that part is sound).
- `kiosk-admin`'s `staffLogin` correctly sends `adminOnly: true` on tenant login (`cloudClient.ts:335`) — unlike `pos-admin`'s equivalent call (see `pos-admin.md` POSADMIN-01), this restricts the login to OWNER/MANAGER roles server-side.
- `kiosk-admin`'s session-epoch mechanism (`sessionEpoch`/`clearTenantSession`/`refreshTenantSession`, lines 227-500) correctly guards against a race where an in-flight silent-refresh response could resurrect a session after an explicit logout — careful, deliberate design.
- Neither kiosk app's `Cargo.toml` declares any Tauri plugin (`shell`, `fs`, `http`, etc. — `features = []` in both) beyond the hand-written commands reviewed above, keeping the native surface small and enumerable.
- `resetTerminal()` in both apps' `cloudClient.ts` fully clears device/restaurant/token local-storage keys so a revoked/unrecognized device correctly falls back to the activation screen rather than being stuck.
