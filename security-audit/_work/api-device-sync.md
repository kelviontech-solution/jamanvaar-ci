## New/independent findings

### DS-01 Any device token can plant a manager-role staff account (or steal every staff PIN hash) via entity-sync — CRITICAL
- Severity: **critical** (CVSS 4.0 approx AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:N ≈ 9.1 — requires only a low-trust device credential, not user interaction, and yields full staff-account forgery across every terminal); Class: CONFIRMED (independently verified at the exact controller/service/DTO level — this corroborates POS-01, POSADMIN-02 and KDSCAP-01 from the client-side slices, which is why it is written up once here as the root-cause server finding)
- CWE-862 (Missing Authorization) / CWE-284 / OWASP API1:2023 Broken Object Level Authorization + API5:2023 Broken Function Level Authorization
- `cloud/api/src/modules/entity-sync/entity-sync.controller.ts:16-34`, `entity-sync.service.ts:33-98`, `dto/push-entity-sync.dto.ts:15-31`
- Attacker/precondition: possession of **any** valid, non-revoked `Device` bearer token for the target restaurant — the lowest-trust terminal type qualifies (e.g. a customer-facing KIOSK or a KDS screen in the kitchen), since `DeviceAuthGuard` only checks that the token hashes to an ACTIVE device of *some* type, not which type.
- Repro (code trace): `POST /api/v1/entity-sync/STAFF_USER` with body `{ events: [{ externalId: "<any-id>", payload: { roleId: "role-manager", pinHash: "<attacker-computed-FNV1a-hash>", fullName: "...", ... } }] }`. The Zod schema (`push-entity-sync.dto.ts:18-24`) validates only `externalId` (string) and `payload: z.record(z.string(), z.unknown())` — completely unstructured, no field-level or entity-type-specific validation, no device-type gate. `pushEvents` → `pushEventsForRestaurant` (`entity-sync.service.ts:48-98`) upserts the record straight into `SyncedEntity` keyed by `(restaurantId, entityType, externalId)`. `STAFF_USER` is **not** in `LAST_CHANGE_WINS_TYPES` (`entity-sync.service.ts:14`), so there is no `updatedAt` conflict check either — the write always lands. Any other terminal (POS, POS_ADMIN, Captain, KDS) at the same restaurant then calls `GET /entity-sync/STAFF_USER?since=...` and, per the client-side slices, applies the returned record as a real local staff user with the attacker-chosen role and PIN hash.
- Expected vs actual: entity types differ enormously in blast radius (a stale coupon vs. a forged manager credential); the endpoint should authorize per entity type (at minimum: only POS_ADMIN/POS may write `STAFF_USER`), not treat "has a device token" as sufficient for all eleven `SYNCABLE_ENTITY_TYPES`.
- Impact: full privilege escalation from a low-trust device to a fleet-wide manager-level staff identity; combined with the weak FNV-1a PIN hashing confirmed by other slices (F-030), the attacker doesn't even need the server to accept a chosen hash — they can compute a valid hash for any 4-digit PIN offline in the same request. Also lets a low-trust device read (`GET`) every existing staff member's PIN hash and role for offline cracking, and tamper with `CUSTOMER` PII, `MENU_ITEM`/`MENU_CATEGORY` prices, and `COUPON` records the same way.
- Root cause: `EntitySyncController`/`EntitySyncService` authorize by "valid device for this restaurant" only; there is no per-entity-type, per-device-type authorization matrix.
- Recommended fix: add a device-type allowlist per `SyncableEntityType` (e.g. only `POS`, `POS_ADMIN` may push `STAFF_USER`; `KIOSK`/`KIOSK_ADMIN` may push `CUSTOMER_FEEDBACK` but not `STAFF_USER`/`MENU_ITEM` price fields) enforced in `EntitySyncController.push`/`EntitySyncService.pushEvents` before the upsert, and add `STAFF_USER` to a stricter validation path (real Zod object schema, not `z.record(unknown)`) so `roleId`/`pinHash` can't be forged wholesale. Server-side, consider not trusting device-originated PIN hashes for privileged roles at all — require an authenticated tenant-JWT session (OWNER/MANAGER) to create or elevate a `MANAGER`/`OWNER`-role `STAFF_USER` record, the same way `TenantAuthService.createStaffUser` already requires `actor.role === 'OWNER'`.
- Regression test: `entity-sync.e2e.spec.ts` — push a `STAFF_USER` event with `roleId: 'role-manager'` from a `KIOSK`-type device token; assert 403 (or that the write is silently dropped/downgraded), then assert a `POS`-type device token performing the same push for a non-privileged role still succeeds.

### DS-02 Order-sync catch-up leaks every branch's orders (incl. customer PII) to any single-branch device
- Severity: **high**; Class: CONFIRMED (root-cause instance of F-043)
- CWE-863 (Incorrect Authorization) / OWASP API1:2023 BOLA
- `cloud/api/src/modules/order-sync/order-sync.service.ts:127-139`
- Attacker/precondition: any device token bound to one branch of a multi-branch restaurant.
- Repro: `GET /api/v1/orders/sync?since=<24h-ago>` — `catchUp`'s `where: { updatedAt: { gt: sinceDate } }` has no `branchId` filter; `runAsTenant` only enforces the restaurant boundary via RLS, not branch. A device at Branch A receives Branch B's orders including `meta.customerName`/`meta.customerPhone` and full item/pricing detail.
- Impact: cross-branch PII and business-data disclosure to any terminal, defeating the multi-branch data-separation the product otherwise implies (branch-scoped devices, `BRANCH_INACTIVE` locking in `DeviceAuthGuard`).
- Root cause: `catchUp`'s query was written restaurant-scoped only; branch scoping was never added even though `Device.branchId` and `SyncedOrder.branchId` both already exist in the schema.
- Fix: add `branchId: device.branchId ?? undefined` to the `where` clause (or, for devices with no branch, restrict to unassigned/branchless orders only) — mirrors the same pattern `DeviceAuthGuard` already uses for `BRANCH_INACTIVE` locking.
- Regression test: seed two branches with one order each; pull `catchUp` as a Branch A device token; assert only Branch A's order is returned.

### DS-03 Order-sync push has no ownership or state-machine guard — any device can overwrite another's settled order
- Severity: medium (chained with DS-02/F-014 it becomes high — an attacker who can read cross-branch orders via DS-02 can also silently rewrite their status/totals via this gap); Class: CONFIRMED
- CWE-841 (Improper Enforcement of Behavioral Workflow) / OWASP API1:2023
- `cloud/api/src/modules/order-sync/order-sync.service.ts:56-85`
- Attacker/precondition: any device token for the restaurant (device-type-agnostic by design, per the controller's own comment at `order-sync.controller.ts:10-13`).
- Repro: push an event with an `externalOrderId` matching an order created and settled (`paymentStatus: 'PAID'`) by a different device; the code path is a plain upsert-by-id with `syncVersion: existing.syncVersion + 1` and **no check** that the pushing device created the order, that the order isn't already in a terminal state, or that the `paymentStatus`/`totalAmount` transition is legal (e.g. PAID → PENDING, or a changed `totalAmount` on an already-paid order).
- Impact: a compromised or rogue low-trust device (KDS, Captain, Kiosk) can revert a POS-settled order's payment status or alter its recorded total in the cloud mirror — this is the exact "stale KDS/Captain push reverts payment status" scenario other agents flagged (KDSCAP-04).
- Root cause: no state-machine/ownership check on order-sync writes; every field is fully overwritable by any device on every push.
- Fix: at minimum, reject a push that would change `paymentStatus` away from a terminal state (`PAID`/`REFUNDED`/`VOID`) unless the pushing device is the order's original `deviceId` or is `POS`/`POS_ADMIN` type; log a `SyncConflict` instead of silently overwriting when `totalAmount`/`paymentStatus` diverge from the stored terminal-state value.
- Regression test: create a `PAID` order via device A; push a conflicting `paymentStatus: 'PENDING'` update via device B; assert the update is rejected or flagged as a conflict, not silently applied.

## Controls verified OK
- `DeviceCommandsController`'s terminal-facing routes (`GET /devices/me/commands`, `POST /devices/me/commands/:id/ack`) correctly scope every query to `device.id` (`getPendingForDevice`/`acknowledgeCommand` in `device-commands.service.ts:133-197`) — a device cannot fetch or acknowledge another device's commands.
- Platform-issued MDM commands (`lock`/`unlock`/`force-logout`/`wipe`) are gated by `PlatformAuthGuard` + `devices:'write'` (PLATFORM_OPS/PLATFORM_OWNER/SUPER_ADMIN only — READ_ONLY/SUPPORT_ADMIN correctly denied since they only hold `devices:'read'`), and `wipeDevice` requires an exact confirmation phrase — `device-commands.controller.ts`, `device-commands.service.ts:104-128`.
- `devices.service.ts:reportHeartbeat` no longer returns the full device row (explicit comment: "This used to return the whole device row, including the stored credential hash") — confirms this leak was already fixed.
- `devices.list()` explicitly strips `deviceTokenHash` before returning rows to the platform UI (`present = (d) => ({ ...d, deviceTokenHash: undefined, ... })`).
- `DeviceAuthGuard` (read in the api-auth slice) already blocks REVOKED devices, suspended restaurants, lapsed subscriptions, disabled per-app entitlements, and MDM-locked devices at every request — this is a solid, centralized enforcement point that `entity-sync`/`order-sync` both sit behind (the gap in DS-01/DS-02/DS-03 is authorization *within* an otherwise-valid device session, not device authentication itself).
