## New/independent findings

### LOCAL-01 The prebuilt `JamanvaarLocalCore.exe` shipped by the "production" release path is built from the unauthenticated LAN server, not the patched one — CRITICAL
- Severity: **critical** (CVSS 4.0 approx AV:A/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H ≈ 9.2 for a LAN-adjacent attacker: no auth, no privileges, full read/write of the restaurant's live order database and ability to inject/alter orders); Class: CONFIRMED
- CWE-306 (Missing Authentication for Critical Function) / CWE-1104 (Use of Unmaintained Third Party/Internal Component) / OWASP API2:2023
- `tooling/local-runtime/sea-config.json:2` (`"main": "tooling/local-runtime/standalone_local_core.cjs"`), `tooling/local-runtime/standalone_local_core.cjs:1-178` (whole file — zero authentication, `HOST = '0.0.0.0'`, `Access-Control-Allow-Origin: *`, `/api/orders` GET/POST with no bearer check, `/api/events` SSE with no auth), `tooling/installers/build_release.cjs:23,276,517` and `tooling/installers/build_production_release.ps1:121,447,451,478` (both copy the tracked `JamanvaarLocalCore.exe` binary directly into the POS/POS-Admin distribution folders)
- Attacker/precondition: any device on the same LAN/WiFi as a restaurant terminal running the `build_release.cjs`/`build_production_release.ps1` packaging path (no credential needed at all — this server has no auth mechanism whatsoever, not even the SERVICE_KEY concept).
- Repro (evidence, not executed): 
  1. `sea-config.json` — the Node.js Single Executable Application config used to produce `JamanvaarLocalCore.exe`/`sea-prep.blob` — declares its entry point as `standalone_local_core.cjs`, the older file that predates the "SEC-005 fix" comment found throughout `local_service.cjs`.
  2. String search inside the tracked 93MB `JamanvaarLocalCore.exe`: contains the literal string `"JAMANVAAR Local Core Engine"` (the `/health` response's `service` field, unique to `standalone_local_core.cjs:113`) and does **not** contain `"SEC-005 fix"` or `"Pairing PIN for new devices"` (both unique to `local_service.cjs`'s comments/console output). This proves the shipped executable was compiled from the unauthenticated source file.
  3. File timestamps corroborate: `JamanvaarLocalCore.exe` was built Sep 1; `local_service.cjs` (containing the auth fix) was last modified Sep 6 — five days *after* the binary was built, and the binary was never rebuilt afterward (still 93MB dated Sep 1 at time of audit).
  4. `build_release.cjs` (`LOCAL_CORE_EXE = .../JamanvaarLocalCore.exe`) and `build_production_release.ps1` — the two scripts whose names most strongly suggest the authoritative "production"/"release" packaging path — both copy this exact stale binary into the distributed POS and POS-Admin folders and wire it up as `coreExe` (a `JamanvaarLocalCore.exe` child process), distinct from the several *other* installer scripts (`build_windows_installers.cjs`, `build_desktop_executables.ps1`, `build_full_native_app_suite.ps1`, `deploy_mcafee_safe_suite.*`, `package_zip_release.cjs`) that correctly bundle and `node`-launch the patched `local_service.cjs` source file instead.
- Expected vs actual: every terminal's local database server should require the same SERVICE_KEY/pairing authentication regardless of which packaging pipeline produced the installer; instead, one of (at least) two real packaging paths in this repository ships a completely open one.
- Impact: on any restaurant using an installer built via `build_release.cjs`/`build_production_release.ps1`, anyone within radio/network range of the restaurant's LAN or WiFi (no restaurant WiFi is guaranteed to be attacker-free — guest WiFi, a nearby table, a compromised IoT device on the same subnet) can, with zero credentials: read every order (including customer name/phone) via `GET /api/orders`, inject arbitrary orders via `POST /api/orders` (the order object is trusted almost verbatim — `order.id`/`order.createdAt` are the only fields defaulted, everything else, including price fields, is whatever the attacker sends), and receive a live feed of all restaurant activity via the unauthenticated SSE stream at `/api/events` or `/events`.
- Root cause: two independently-evolving copies of the same LAN server exist in the tree; a security fix was applied to one and never propagated to the other, and the prebuilt binary was never rebuilt or removed after the fix landed.
- Recommended fix (in order of preference): (1) delete `standalone_local_core.cjs`, `sea-config.json`, `sea-prep.blob`, and the tracked `JamanvaarLocalCore.exe`, and repoint `build_release.cjs`/`build_production_release.ps1` at `local_service.cjs` like every other installer script already does — eliminates the divergence entirely; (2) if the SEA/single-binary packaging is still wanted for some deployment shape, regenerate it from `local_service.cjs` and stop committing the built binary at all (build it in CI, sign it, publish it as a release artifact — not source-controlled); (3) either way, stop committing multi-hundred-MB binaries to git (use Git LFS or a release-asset store) so a stale, silently-divergent copy can't happen again unnoticed.
- Regression test: a CI check that fails the build if `standalone_local_core.cjs` (or any file lacking the `SEC-005`/`isAuthorized` pattern) is referenced by any installer script, plus a smoke test that launches whatever `build_release.cjs` actually packages and asserts `GET /api/orders` returns 401 without a key.

### LOCAL-02 `/devices/pair` pairing PIN has no rate limiting (companion detail to F-009)
- Severity: medium; Class: CONFIRMED — see F-009 row above for full detail; recorded here only to give it a regression-test hook.
- Fix: track failed-pairing attempts per source IP (or globally, since this is a single-tenant LAN service) and lock out / exponentially back off after e.g. 10 wrong PINs; consider a longer PIN or requiring a short cooldown between attempts server-side, not just client-side throttling (which an attacker scripting requests directly would ignore).
- Regression test: 20 rapid wrong-PIN `POST /devices/pair` calls should start returning 429 (or an increasing delay) well before the full keyspace is exhausted.

## Controls verified OK
- `local_service.cjs` writes the DB file via a temp-file-then-atomic-rename pattern with a rolling `.bak` copy (`saveDb()`, lines 81-93) — good crash-safety, prevents a truncated/corrupt `live_db.json` on power loss mid-write.
- `local_service.cjs`'s `POST /api/orders` idempotency map correctly returns the existing order on a retried request with the same `idempotencyKey` rather than double-creating it (lines 306-315).
- `.local_service_key` is correctly gitignored and was not found tracked in git history at HEAD (verified via `git check-ignore`/`git ls-files`, not a full history scan for historical commits — see `supply-chain-secrets` slice for that).
- `pin.ts`'s `generateUniquePin` explicitly deprioritizes weak PINs (`0000`, `1111`, `1234`, `1212`, `0001`) when auto-generating a new one, and salts the hash per-restaurant so the same PIN doesn't hash identically across tenants.
- `command_pipeline.ts`'s idempotency cache (`executedCommandIds`/`commandResultsCache`) correctly short-circuits a retried command with the same `commandId` rather than re-executing side effects.
