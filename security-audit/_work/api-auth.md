## New/independent findings

### AUTH-01 Tenant device-token check can be skipped when only `deviceId` is known
- Severity: **medium** (CVSS 4.0 approx 6.5, AV:N/AC:L/AT:N/PR:L/UI:N/VC:L/VI:L/VA:N); Class: CONFIRMED
- CWE-287 (Improper Authentication) / OWASP API2:2023 Broken Authentication
- `cloud/api/src/modules/tenant-auth/tenant-auth.service.ts:289-310`
- Attacker/precondition: holds valid email+password for *any* user at a restaurant (even a low-privilege STAFF account they were legitimately given), and knows the `id` of an existing ACTIVE device at that restaurant (device IDs are exposed by `/support/search` to any `support:read` platform role, see F-004; they may also be visible in client-side network traffic/localStorage on other terminals).
- Repro (code trace): `POST /tenant-auth/login` with `{email, password, deviceId}` and **no** `deviceToken`. Line 301-309: since `deviceToken` is falsy, the `if (deviceToken && activeDevice.deviceTokenHash)` branch is skipped and the `else` unconditionally sets `isDeviceActive = true`.
- Expected: a session should only bind to a device identity (`did` claim, later trusted by `assertSessionStillAllowed`/audit trails as "this terminal") when the caller proves possession of that device's token.
- Impact: an attacker with any valid tenant credential can mint a session that impersonates a specific, different terminal without ever holding that terminal's token — weakens the "device revocation ends that terminal's session" security model (`DeviceAuthGuard`/`assertSessionStillAllowed` treat `did` as trustworthy) and confuses audit trails (`TENANT_LOGIN` logs `deviceId: activeDevice.id`, attributing the login to the wrong terminal).
- Root cause: device-token verification is optional in the login flow instead of mandatory whenever `deviceId` is present.
- Fix: require `deviceToken` whenever `deviceId` is supplied; if it's missing or doesn't match, fall through to the `ACTIVATION_REQUIRED` branch (as already happens when no active device is found at all) rather than silently trusting the identity claim.
- Regression test: `tenant-auth.e2e.spec.ts` — login with a real user + an existing device's `id` but a wrong/omitted `deviceToken` must return `ACTIVATION_REQUIRED`, not `LOGIN_SUCCESS`.

### AUTH-02 `resend-invite` lets a SUPER_ADMIN take over a pending PLATFORM_OWNER invite
- Severity: **medium**; Class: CONFIRMED (cross-checked against `super-admin-web.md` SAW-07, same root cause, verified independently here at the service layer)
- CWE-269 (Improper Privilege Management) / OWASP API5:2023 Broken Function Level Authorization
- `cloud/api/src/modules/platform-users/platform-users.service.ts:161-209` (`resendInvite`) vs `:221-299` (`updateRole`, `setStatus`, which both call `assertActorIsOwner` when `existing.role === 'PLATFORM_OWNER'`)
- Attacker/precondition: an authenticated SUPER_ADMIN (not PLATFORM_OWNER) platform account, with a still-`PENDING_ACTIVATION` PLATFORM_OWNER invite existing in the system (e.g. one sent by the real owner to a co-founder who hasn't clicked it yet).
- Repro: `POST /api/v1/platform-users/:id/resend-invite` as SUPER_ADMIN, targeting the pending owner's user id. `resendInvite` only calls `assertCanManageTeam` (allows PLATFORM_OWNER **or** SUPER_ADMIN) and never checks `existing.role`. The response includes the plaintext `activationToken`. Then `POST /api/v1/platform-users/activate` (public, no guard) with that email/token/a new password sets the password and activates the account — now the attacker controls a PLATFORM_OWNER-status login (though the account's *role* field was already `PLATFORM_OWNER` from the original invite, so this is a full account takeover of an owner-level identity, not merely a role change).
- Expected vs actual: `updateRole`/`setStatus` correctly gate any mutation touching a `PLATFORM_OWNER` row behind `assertActorIsOwner`; `resendInvite` does not apply the same rule even though it produces an equally powerful credential (a fresh activation token good for 7 days).
- Impact: privilege escalation from SUPER_ADMIN to (a second, attacker-controlled) PLATFORM_OWNER identity, bypassing the "only a Platform Owner can grant the Platform Owner role" invariant the rest of the module enforces.
- Root cause: missing `assertActorIsOwner` check in `resendInvite` for owner-role targets.
- Fix: add the same `if (existing.role === 'PLATFORM_OWNER') assertActorIsOwner(actor, 'resend an invite to a Platform Owner')` guard used elsewhere in this service.
- Regression test: SUPER_ADMIN calling `resend-invite` on a pending `PLATFORM_OWNER` user must 403; PLATFORM_OWNER calling it must still succeed.

### AUTH-03 Tenant login timing differs for "unknown user" vs "wrong password" (restaurant-scoped)
- Severity: low; Class: CONFIRMED
- CWE-208 (Observable Timing Discrepancy) / OWASP API2:2023
- `cloud/api/src/modules/tenant-auth/tenant-auth.service.ts:250-274`
- Attacker/precondition: network position to measure response latency to `POST /tenant-auth/login` with a fixed `restaurantId`.
- Repro: when `candidates` is empty (no user with that email at that restaurant), the `for` loop body never runs, so zero `bcrypt.compare` calls happen (~sub-millisecond) versus at least one ~60-80ms bcrypt compare when the email exists. Platform login (`platform-auth.service.ts:88-112`) deliberately avoids this by always running `bcrypt.compare` against a fixed dummy hash — the same fix was never applied to tenant login.
- Impact: allows enumerating valid staff emails per restaurant; low severity because restaurant emails are typically known internally already and this doesn't itself grant access.
- Fix: mirror the platform login's fixed-dummy-hash pattern — always await one `bcrypt.compare` even when `candidates` is empty.
- Regression test: measure/assert response paths execute a compare call in both cases (or assert via a spy) rather than timing directly in CI.

## Controls verified OK
- `PlatformAuthGuard`/`TenantAuthGuard` correctly pin `issuer`+`audience` per realm; cross-realm token reuse is rejected (`platform-auth.guard.ts:43-47`, `tenant-auth.guard.ts:39-43`).
- Platform login is enumeration-resistant (fixed dummy-hash compare) — `platform-auth.service.ts:91-112`.
- Session revocation on password change (`PLATFORM_PASSWORD_CHANGED` terminates every other session; tenant `changePassword`/`resetPassword` revoke all refresh tokens) — `platform-auth.service.ts:228-252`, `tenant-auth.service.ts:774-797, 865-875`.
- `PlatformAuthGuard` checks `PlatformRefreshToken.terminatedAt` per-session so a revoked session's *already-issued* access token dies within the request, not just at its 15-minute natural expiry — `platform-auth.guard.ts:57-67`.
- Password-reset OTP comparison uses `timingSafeEqual`, has a 5-attempt cap and a 15-minute expiry, and a 60s resend cooldown — `tenant-auth.service.ts:847-863`. (The hash itself, unsalted SHA-256 of a 6-digit code, is still crackable in ~1s if leaked via `/support/search` — that's the AD-01/SAW-01 finding, not this control.)
- `env.validation.ts` fails boot on a short/missing `JWT_ACCESS_SECRET` (min 32 chars) rather than defaulting to something guessable.
- Activation-invite link puts the one-time token in the URL **fragment**, not the query string, specifically to keep it out of server logs/Referer — `platform-users/activation-url.ts:1-10`.
- `EntitlementGuard`'s insecure header fallback is currently dead code (not wired to any route) — confirmed via repo-wide search for `RequireEntitlement`/`UseGuards(EntitlementGuard)`.
