## New/independent findings

### SC-01 A real-looking SUPER_ADMIN credential and its plaintext password are committed to git
- Severity: **high** (capped below critical only because this audit cannot confirm from source alone whether the credential is valid against any reachable/shared database today — if it is, this is critical); Class: CONFIRMED as a committed secret, severity of *live* impact is `needs_validation`
- CWE-798 (Use of Hard-coded Credentials) / CWE-312 (Cleartext Storage of Sensitive Information) / OWASP A07:2021
- `cloud/api/prisma/_tmp_user.ts:1-23` (tracked, added in commit `9ddb563`, "chore: add remaining local files (browser-test artifacts, one-off dev scripts)"), `AUDIT_BRIEF.md:20` (repo root, tracked)
- Evidence: `_tmp_user.ts` is a one-off script that `bcrypt.hash`es the literal string `'LiveVerify-9f3a-Temp!'` and upserts a `PlatformUser` with `email: 'live-verify@jamanvaar.local'`, `role: 'SUPER_ADMIN'`, `status: 'ACTIVE'`. The exact same plaintext email/password pair is independently committed in `AUDIT_BRIEF.md:20` ("Super Admin login: `live-verify@jamanvaar.local` / `LiveVerify-9f3a-Temp!` (role SUPER_ADMIN)"), alongside three staff PINs and five unredeemed activation key codes in the same file (lines 21-22).
- Expected vs actual: `cloud/api/.env.example`'s own comment is explicit that "there is no demo/bypass login" and that seed credentials must be set by the operator (`SEED_SUPER_ADMIN_EMAIL`/`SEED_SUPER_ADMIN_PASSWORD`) — `_tmp_user.ts` is a rogue script that bypasses that entire design by hardcoding and committing a working credential directly.
- Impact: anyone with read access to this repository (or its git history, even if these files are deleted later — git history retains them until a history rewrite + force-push + the old objects are garbage-collected everywhere they were cloned/mirrored) has a real SUPER_ADMIN email+password pair. If this script was ever run against a shared, network-reachable database (dev, staging, demo, or — worst case — production), that account is live and grants full platform-owner-equivalent access (per `common/rbac/access.ts`, `SUPER_ADMIN` has write access to every area except `settings`). Even if today it only touches a local/throwaway database, the same credential pattern (predictable "for verification" naming) risks being reused or the script rerun against a more permanent environment later.
- Root cause: a one-off verification/debug script with a hardcoded credential was committed instead of being kept out of version control (should have been gitignored, like `.local_service_key` correctly is) or, better, parameterized via environment variables the way the real seed script (`prisma/seed.ts`) already is.
- Recommended fix: (1) treat this credential as **compromised now** — rotate/disable the `live-verify@jamanvaar.local` PlatformUser in every environment where `_tmp_user.ts` may have been run (production, staging, demo, shared dev), regardless of whether this audit can prove it's live; (2) delete `_tmp_user.ts` and `_tmp_rel.ts` from the working tree and from git history (`git filter-repo`/BFG, then force-push and have every clone re-fetch) since deleting the file alone leaves the secret in history; (3) also rotate/redact the staff PINs and activation keys listed in `AUDIT_BRIEF.md` if that file is or was ever pushed to a shared/public remote, and stop committing files with live operational credentials — link to a local-only, gitignored notes file instead; (4) add a pre-commit/CI secret scanner (gitleaks, trufflehog, or GitHub secret scanning if the remote supports it) so a future one-off script with a hardcoded credential is caught before merge.
- Regression test: not applicable to unit tests — recommend a CI step running a secret-pattern scanner over the diff on every PR.

### SC-02 Installer silently adds a self-signed root CA to the installing user's Windows trust store
- Severity: medium (requires the installer to already be run locally with the user's own privileges — not a remote vulnerability — but it is a real, undisclosed expansion of what that user's Windows session will trust afterward); Class: CONFIRMED
- CWE-295 (Improper Certificate Validation) / CWE-296 (Improper Following of a Certificate's Chain of Trust) — installer-side equivalent
- `tooling/installers/build_windows_installers.cjs:658-670`
- Repro (evidence, not executed): the PowerShell block generated and run by this build script does: if no existing `KELVIONTECH`-subject cert is found under `Cert:\CurrentUser\My`, generate a new self-signed `CodeSigningCert` (`New-SelfSignedCertificate ... -Subject 'CN=KELVIONTECH INC., O=JAMANVAAR, C=IN'`), export it, then run `Import-Certificate -FilePath $tmpCert -CertStoreLocation Cert:\CurrentUser\Root` **and** `-CertStoreLocation Cert:\CurrentUser\TrustedPublisher`. This happens automatically as part of building/signing the installer, with no prompt shown to (or consent obtained from) whoever's Windows profile is running the build — and depending on which script actually invokes this at install time on a customer machine (vs. only at build time on a developer machine — **not fully traced in this pass**, flagged below), it may run on every end-customer's machine too, not just developer build machines.
- Expected vs actual: a `TrustedPublisher` entry alone is the normal, narrower way to make Windows/SmartScreen trust a specific signer for *executables signed by that specific certificate* without a warning; adding the same self-signed cert to `Root` (Trusted **Root Certification Authorities**) is a broader trust grant — Windows will now treat this certificate as a root of trust, not just an accepted single publisher, for that user profile. Because `New-SelfSignedCertificate -Type CodeSigningCert` scopes the certificate's EKU to code-signing, the practical blast radius is narrower than a general-purpose root (it can't be used to impersonate arbitrary TLS websites), but it does mean any future executable signed with the same private key — including by anyone else who obtains that key from `CurrentUser\My`/the exported `.cer`/private key material, e.g. via a compromised build machine — will be silently trusted as "from a trusted root" rather than flagged, on every machine where this installer ran.
- Impact: undisclosed, automatic trust-store modification is itself a finding (informed consent / least-privilege principle) independent of whether the private key is ever actually compromised; if it *is* run on end-customer machines (not just CI/dev), this is a supply-chain trust expansion happening silently on every install.
- Root cause: using `Cert:\CurrentUser\Root` instead of only `TrustedPublisher` (the narrower store actually needed to suppress a SmartScreen warning for a specific already-known publisher) for a self-signed development certificate.
- Recommended fix: for real releases, use a properly purchased/issued Authenticode code-signing certificate from a recognized CA instead of a self-signed one (eliminates the need to touch the trust store at all); if a self-signed cert must be used for internal/dev builds, import it only into `TrustedPublisher` (never `Root`), and make the trust-store modification an explicit, logged, consented step rather than a silent side effect of the signing script.
- Regression test: N/A (build/release process hardening) — could add a CI check that greps for `CurrentUser\Root`/`LocalMachine\Root` in any installer/signing script and fails the build if found outside an explicitly-reviewed exception list.

### SC-03 Several high/moderate npm advisories are present in resolved dependencies (root workspace)
- Severity: low-medium — see per-package notes; Class: CONFIRMED (advisory data), reachability not individually traced for each package
- CWE-1104 / OWASP A06:2021 (Vulnerable and Outdated Components)
- `npm audit --omit=dev --json` at repo root, 11 advisories: `multer` (**high** — 3 DoS advisories: incomplete cleanup, resource exhaustion, uncontrolled recursion), `lodash` (**high** — code injection via `_.template`, prototype pollution via `_.unset`/`_.omit`), `@nestjs/platform-express` (**high**, via the `multer`/`body-parser` chain), `@nestjs/core` (moderate, injection in an error-output path), `@nestjs/common` (moderate, via `file-type`), `file-type` (moderate — ASF-parser infinite loop, ZIP-bomb DoS), `qs` (moderate — 3 DoS-class advisories), `react-router`/`react-router-dom` (moderate — open redirect via backslash in `<Link>`/`useNavigate`, arbitrary constructor injection via SSR error deserialization), `body-parser` (low — size-limit bypass). All 11 report `fixAvailable: true` per npm's resolver.
- Impact/reachability notes (not individually verified this pass, flagged for follow-up):
  - `multer` is directly relevant: `cloud/api` handles file uploads (master-catalog images, tenant backup restore uploads per `api-license-billing.md` LB-06) — a DoS-class multer bug is plausibly reachable by any authenticated (or, per LB-06, under-authorized) caller of those upload endpoints.
  - `lodash`'s prototype-pollution/code-injection advisories matter most if any code path calls `_.template`, `_.unset`, or `_.omit` with attacker-influenced input — not traced to a specific call site in this pass.
  - `react-router`'s open-redirect advisory is relevant to whichever frontend(s) use it (likely `cloud/super-admin-web` and/or the Tauri apps) — worth checking against the `super-admin-web.md` slice's "no open redirects found" control, since that finding predates knowing this specific CVE class exists in the resolved version.
  - `qs`/`body-parser` DoS advisories are transitively pulled in by Express/NestJS itself; low incremental risk beyond what a public HTTP server already accepts, but free to fix.
- Recommended fix: run `npm audit fix` (all 11 report a fix available) in a branch, run the full test suite (`npm test` — baseline already established at 876 passing tests), and verify no breaking API changes in the bumped majors before merging; prioritize `multer`/`@nestjs/platform-express` given direct upload-endpoint reachability.
- Regression test: re-run `npm audit --omit=dev` in CI on a schedule (or per-PR) and fail on new high/critical advisories with no accepted-risk annotation.
