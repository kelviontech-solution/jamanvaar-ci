# QR Admin — page, feature and UI audit

**Implementation follow-up:** [Fixes and shared loyalty CRM](IMPLEMENTATION.md). The assessment below preserves the original findings and evidence; the follow-up records the changes and regression results.

14 October 2026. This audit inspected the current local workspace, following the previous full-app fixes. It tested the standalone `/qr/admin/` experience against the compiled API and an isolated test database. **This is not a test of the currently deployed production build.** No application source fixes were made in this assessment.

The main layouts fit desktop, tablet and phone. Many core features work. Two important problems remain: older unpaid orders disappear behind the latest-50-order limit, and the quick cash-confirmation dialog asks for the original bill total after a partial collection. Draft protection and popup accessibility also need improvement.

## What was checked

- All **14 main pages** and **6 additional advanced sections**: 20 distinct page/section states.
- Desktop **1440 × 960**, tablet **768 × 1024**, phone **390 × 844**.
- **120 captures** across the base-license and optional-features-enabled fixture configurations. Locked optional features were not counted as broken features.
- Actual browser actions for authentication, menu search/edit/publication, CSV validation, branding, ordering rules, QR preview/download/design, analytics validation, service requests, pickup settings, translations, promotions, counted stock, collections and CSV export.
- **96 backend integration tests passed** across QR menu control, operations, advanced modules, mobile payments and feature requests. Those include concurrency, isolation, retries, refunds, stock reservations, group sessions, loyalty and entitlements. Provider transport was simulated; these are not real bank/UPI/SMS delivery tests.
- Screenshots were visually inspected as well as checking DOM geometry and API outcomes. Initial harness failures were corrected or classified; opening a dialog or listing a button is not treated as successful completion of its business flow.

Evidence: [licensed page/viewport matrix](evidence/licensed-page-matrix.json), [test actions](evidence/tests.jsonl), [observed defects](evidence/observations.jsonl). Scripts and test commands are listed in [VERIFICATION.md](VERIFICATION.md).

## Login, activation and recovery

Login, Activate and Recover were captured on desktop and phone. Activated-console sign out → owner sign in succeeded without demanding a new activation key. Wrong password displayed a rejection and did not enter QR Admin. Missing recovery identity was blocked by required-field validation.

A fresh console activation and a real recovery email/reset were not completed in this browser run. Existing backend entitlement/recovery checks are separate evidence. Real SMTP delivery and administrator-assisted reassignment still require their own environment.

## UI assessment

The rebuilt workspace has a usable sidebar, consistent navy/orange styling, a compact mobile branch header and readable main cards. In the **60 optional-feature-enabled page/viewport captures**, there was **no document horizontal overflow, no duplicate IDs and no unnamed visible buttons**. That does not prove focus/modal behavior: QR06/QR07 are real defects even though static pages fit.

The initial DOM scanner incorrectly counted controls inside closed details/off-canvas navigation as unnamed. The refined scanner checks CSS visibility and text content. Those initial numbers are not product findings.

Most useful UI changes:

1. Keep live order, counter debt and service request actions prominent; put configuration behind clear task groups.
2. Split draft menu editing from published visibility, and paginate both.
3. Use one branch scope indicator; explain restaurant-wide menu changes beside Publish.
4. Increase touch targets and standardize all popups through the shared modal.
5. Replace raw enum/currency placeholders with consistent customer/staff language.
6. Add actual menu previews, reusable branded QR cards and clearer colour controls. Keep demo data clearly identified.

## Boundaries and remaining acceptance

This audit does not claim every possible button permutation is working. The page matrix covers every current main page and advanced subsection; the feature matrix names actual committed scenarios. Live online payment was simulated. Real UPI app return, bank settlement, SMTP/SMS/WhatsApp transport, physical QR scans/printers, scheduled-pickup handover, fresh activation, production HTTPS/proxy/service-worker behavior and peak restaurant traffic remain separate acceptance checks.

Optional-license configuration was restored after the audit. Temporary order-limit records were deleted. All other test writes were on the existing isolated QA tenant, using audit-labelled data. Existing application edits were preserved.
